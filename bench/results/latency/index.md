# P4 — Per-call latency distribution artifacts

Pinned-host CPU profile data is in [`../perf/`](../perf/); this directory
holds the latency-distribution artifacts that replace the earlier
"p99 spans 14–78 ns" point-estimate claim with a real percentile sweep
per signal.

## How these were produced

Every artifact in this directory was generated by `bench/latency_bench`
(source in [`bench/latency_bench.cpp`](../../../bench/latency_bench.cpp))
using the HdrHistogram-style histogram defined in
[`bench/latency_histogram.{h,cpp}`](../../../bench/latency_histogram.h).
Each event is timed individually with `std::chrono::steady_clock`; no
batching, no division-by-batch-size, no rolling means.

Two measurement modes are reported:

- **closed-loop** (`{stem}_latency_histogram.{csv,md,svg}` at the root of
  this directory): back-to-back calls, no rate gate. Measures the JIT's
  intrinsic per-call cost. Tail latency in this mode reflects only
  CPU-level events (cache misses, page faults, branch mispredicts, brief
  preemptions) — *not* queueing.
- **open-loop CO-aware** (`co_*Mhz/{stem}_latency_histogram.{csv,md,svg}`):
  events scheduled at a fixed rate, spin-wait until target arrival,
  recorded latency = completion − target. This is the standard wrk2 /
  HdrHistogram pattern. Once a stall pushes us past target, *subsequent*
  events' latencies absorb the queueing delay — the Coordinated-Omission
  correction. The rate is chosen per signal at ~60% of closed-loop peak
  throughput so the gate is reachable but tight enough to expose OS
  jitter.

Full methodology and rationale: [`docs/latency_distribution.md`](../../../docs/latency_distribution.md).

## Headline numbers (JIT, closed-loop, 1 M events)

| Signal | p50 | p99 | p99.9 | p99.99 | max |
|---|---:|---:|---:|---:|---:|
| `spread_signal`      | **19 ns**  | 22 ns   | 29 ns   | 164 ns   | 123 µs |
| `filtered_momentum`  | **148 ns** | 180 ns  | 220 ns  | 6.5 µs   | 328 µs |
| `profile_canonical`  | **180 ns** | 236 ns  | 312 ns  | 10.5 µs  | 4.5 ms |

The `p99.99` column is the part the old "p99 spans X–Y ns" claim hid.
On a non-isolated, non-pinned WSL2 host, individual events occasionally
get preempted by the scheduler for several microseconds; that shows up
as a clean step in the CDF (see the SVGs). On a real low-latency host —
isolcpus + irq affinity + no governor scaling — those tail samples
collapse by an order of magnitude or more; the artifact's job is to
*show* this honestly, not to claim it isn't there.

## What the JIT actually saves

Per-signal interpreter-vs-JIT speedup at p50 (closed-loop):

| Signal | interp p50 | jit p50 | speedup |
|---|---:|---:|---:|
| `spread_signal`      | 26 ns | 19 ns | 1.4× |
| `filtered_momentum`  | 280 ns | 148 ns | 1.9× |
| `profile_canonical`  | 328 ns | 180 ns | 1.8× |

These numbers are smaller than the throughput-based speedups in
`pinned_host_speedup.md` because per-call latency on a non-isolated host
is bounded below by clock-call overhead (≈10 ns for the surrounding
`steady_clock::now()` pair).

## How to regenerate

```bash
make -j8 latency_bench
bash bench/run_latency_artifacts.sh          # closed-loop only
bash bench/run_latency_artifacts.sh --co     # closed-loop + CO-aware
```

CSV format (per non-empty histogram bucket):

```
label,bucket_index,lo_ns,hi_ns,count,cum_count,cum_fraction
```

The SVGs are self-contained vector CDFs (no external CSS / JS / fonts)
suitable for embedding into anything that can render SVG.
