# Tiered specialization (P1)

This document explains the **two-tier JIT** that lives behind
`jitse::TieredProgramJit`. The tiering is a profile-guided optimization that
trades a one-time compile cost (after the program reaches its warm-up
threshold) for a measurably faster hot loop on the warm path.

The mechanism is intentionally narrow: the only profile signal we use is the
static fact that "this stateful operator has been ticked enough times to be
warm". We do not collect runtime histograms, branch-frequency counters, or
trace information; the whole "profile" is determined at compile time by
walking the AST. That keeps the implementation small and safe to ship.

For the IR-level evidence backing the claims in this doc see
`bench/results/lowering_evidence/tiered_specialization.md`, which is
auto-generated by `bench/stateful_lowering_ir_diff.cpp` and pins the
`select` / `icmp eq i64` / `jit_rt_*` counts to a specific signal.

---

## Why have a tier-2 at all?

P0 lowered the opaque `jit_rt_sma` / `jit_rt_ema_alpha` / `jit_rt_lag`
runtime calls into typed LLVM IR. Once they were IR, LLVM could finally
inline, CSE, and vectorize them. But the lowered IR still has to handle
two transient states that only matter during program warm-up:

* `tick_index == 0`  -- "EMA has never been written; emit `x` instead of the
  recurrence."
* `count < period`   -- "SMA / LAG don't yet have a full window; emit NaN."

Both of those branches turn into a `select` (or in the SMA case a
`select` plus an `icmp eq i64` plus a divide-by-`count` instead of by
`period`). After the operator reaches its warm window those branches are
**provably dead**, but LLVM has no way to know that, so it keeps them
in the hot loop forever.

P1 closes that gap. After every warm-safe stateful node has reached its
warm window, we promote to a *specialized* compile that asks codegen to
**skip emitting the warmup guards in the first place**. LLVM then sees
straight-line IR and produces tighter code: the warm SMA becomes
`sum = (sum + x) - old; sum / period`, the warm EMA becomes a single
fused-multiply-add, and the warm LAG becomes a ring-buffer load + store.

The win on `momentum_signal.sig` measured locally (`--tier=specialized`
vs `--tier=baseline`) is ~30% throughput. The win on `filtered_momentum`
is smaller because most of the work in that signal is conditional EMA
work that P1 deliberately does **not** specialize (see "What is
warm-safe?" below).

## What is the warm threshold?

`jitse::ComputeProgramWarmupThreshold(signals)` walks the AST of every
signal in the program and returns:

```
max(
  for each stateful op in any signal:
    sma(_, p) -> p          (need a full window of `p` samples to be warm)
    lag(_, p) -> p          (need to have written `p` values into the ring)
    ema(_, _) -> 1          (warm after the first tick)
)
```

Once the program has been ticked `WarmupTickThreshold()` times against a
contiguous data stream, **every warm-safe stateful node** in the program
is in its steady state. That is the precondition for invoking the
specialized function.

The caller is responsible for ensuring the precondition holds before
calling `Promote()`-and-running. In the benchmark we do that by ticking
the baseline function against the same `SignalContext` we'll later
measure against; in the production wrapper the caller's runtime would
do the same.

---

## What is "warm-safe"?

Not every stateful op in a program is guaranteed to be warm at the
program-wide warmup threshold. Consider:

```
signal filtered = if abs(price) > threshold then ema(price, 30) else 0.0;
```

The `ema(price, 30)` only ticks on the branches where the condition is
true. If the program runs 30 ticks and the condition was only true 5 of
them, that EMA is not warm even though the program-wide threshold has
been hit.

`CollectWarmSafeStatefulCalls(signals)` walks the AST and identifies
exactly the stateful `FunctionCall`s that are **not** lexically nested
inside a `Conditional`'s `then_branch` or `else_branch`. Only those are
specialized. Anything nested under a conditional keeps the full
`is_init` / `is_full` guards in the specialized compile, exactly like
the baseline.

This is conservative on purpose: a more aggressive analysis could
specialize a conditional stateful op too, but it would have to insert a
per-node "has this been ticked at least `period` times?" runtime check.
Empirically, conditional stateful ops are rare in our DSL, and the
correctness of the warm-loop guarantee is more valuable than catching
the last few percent of branches.

You can see the conservative behavior in the IR-evidence artifact: on
`filtered_momentum`, two of the 8 EMAs survive the specialization
because they sit under conditional branches.

## What does the specialized IR actually look like?

`bench/stateful_lowering_ir_diff` dumps post-O2 IR for the three modes
side-by-side. The two diagnostic counters we track are:

* `select`     -- materialized warmup-branch results.
* `icmp eq i64` -- the `tick_index == 0` / `count == period` guard tests.

For `examples/filtered_momentum.sig` (measured locally):

| primitive       | `lowering=none` | `lowering=all` | `tier=specialized` |
|-----------------|-----------------|----------------|--------------------|
| `select`        | 0               | 8              | 2                  |
| `icmp eq i64`   | 0               | 8              | 2                  |
| `jit_rt_ema_alpha` | 8           | 0              | 0                  |

The `none` row is 0 / 0 because the warmup guards still live inside the
opaque runtime call. The `all` row is the cost we paid for lowering:
LLVM has to materialize the guards. The `specialized` row is what
`assume_warm` buys us -- 6 of the 8 guard pairs are gone, and only the
guards under conditional branches remain. **That is the win.**

For a "no-conditionals" signal like a pure stack of SMAs+EMAs, the
specialized column drops to 0 / 0 / 0 (see the parity test cases
`swap_sma_only_period_10`, `swap_mixed_all_three`, etc.).

## How is parity guaranteed?

`test/tiered_specialization_parity_test.cpp` is the gate. For each test
case it:

1. Builds two `MultiSymbolSignalContext`s from the same seed.
2. Drives both contexts with the same deterministic stream.
3. Path A uses only the baseline function for the full stream.
4. Path B runs the baseline function for `WarmupTickThreshold()` ticks,
   calls `Promote()`, and switches to the specialized function for the
   rest of the stream.
5. Asserts `output[A][t] == output[B][t]` bit-for-bit for every `t >=
   WarmupTickThreshold()`.

This is a strict bit-equality gate, not a `|a - b| < eps` check. The
specialized SMA reuses the baseline's arithmetic order
(`(sum + x) - old`) precisely so that floating-point associativity does
not introduce a `1e-13` drift. We pay attention to that order on
purpose.

The test also asserts the IR-level invariants -- specialized
`select` counts must be `<=` the baseline counts on every case, and on
the no-conditional cases they must hit zero. That gate is what catches
regressions where someone "optimizes" the lowered IR in a way that
silently re-introduces the warmup branch in the specialized compile.

## API summary

```cpp
#include "jit_compiler.h"

jitse::SymbolTable symbols;
std::vector<jitse::SignalDef> signals = /* parse + inline */;

// IMPORTANT: caller is responsible for these two steps. TieredProgramJit
// does NOT clone the AST; both the baseline and the specialized compile
// run against the same FunctionCall* node graph that the caller's
// SignalContext was prewarmed against. If you skip these, the
// specialized compile will trip a "RingStatsPushPrepared called before
// state prewarm" runtime assertion.
jitse::AllocateProgramNodeIds(signals);
for (auto& s : signals) jitse::BindSymbolIds(s, symbols);

jitse::TieredProgramJit tjit;
tjit.Compile(signals, symbols, jitse::StatefulLoweringFlags::kAll);

// `program_fn` points at the baseline compile. Tick it until the program
// has reached its warm-up threshold (or longer, that's the safe direction).
auto* program_fn = tjit.CurrentFunction();
const std::int64_t threshold = tjit.WarmupTickThreshold();
for (std::int64_t i = 0; i < threshold; ++i) {
  program_fn(&market, &ctx, /*symbol_index=*/0, outputs);
  /* update market */
}

// Atomic swap to the specialized compile.
if (tjit.Promote()) {
  program_fn = tjit.CurrentFunction();
}

// Hot loop -- straight-line IR for warm-safe stateful nodes.
for (;;) {
  program_fn(&market, &ctx, 0, outputs);
  /* ... */
}
```

`Promote()` is a one-way transition. Once a `TieredProgramJit` has been
promoted, calling `CurrentFunction()` always returns the specialized
function. There is no "demote" path -- the only failure mode we care
about is "specialized compile didn't produce a faster function", which
is a benchmark question, not a correctness question.

## Reproducing

```bash
# Build
cmake -S . -B build-wsl -DCMAKE_BUILD_TYPE=Release
cmake --build build-wsl -j

# Parity gate (must be PASSED)
./build-wsl/tiered_specialization_parity_test

# IR-level evidence + auto-generated artifact
./build-wsl/stateful_lowering_ir_diff examples/filtered_momentum.sig \
    bench/results/lowering_evidence

# Throughput comparison
./build-wsl/signal_benchmark --tier=baseline    examples/momentum_signal.sig 1000000
./build-wsl/signal_benchmark --tier=specialized examples/momentum_signal.sig 1000000
```

The benchmark prints `tier=baseline` or `tier=specialized`, along with
`specialized_warmup_ticks=<N>` so the `jit_throughput` row can be
compared apples-to-apples (the specialized run warms its context with
`<N>` baseline ticks before the timed loop starts).
